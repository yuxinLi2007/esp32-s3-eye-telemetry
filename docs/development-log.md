## 二、三条一直用到的判断准则

### 1. 同一个事实不要存两处

`trust_level` 由 `ntp_synced` + `ntp_sync_age_s` 现场算出，**不落库成字段**。
采集开关的当前状态取 `control_log` 的最后一条，**不另设单行表**。

理由一样：存两份，早晚会漂移，而漂移之后没有权威可依据。

### 2. 派生值只能有一个来源

界面里的 `trustOf()` 与服务端的 `trust_level()` 是同一套规则写了两遍。
这是刻意的取舍——前端不能依赖后端每次都算好（逐点打标要用行内字段），
但两边的阈值常量都加了"与某某保持一致"的注释互相指名。**代价是改阈值要改两处**，
换成共享配置就得引入构建步骤，对一个单文件、无构建的界面来说不划算。

### 3. 不确定就实测，别抄文档

`ACCEL_LSB_PER_G`、`MIC_DBFS_TO_SPL`、`NTP_RESYNC_MS` 全都是实测定出来的，
注释里写明了怎么测的、初值是多少、为什么改。硬件项目里"数据手册说 8192"
和"这块板子实际是 13189"是两回事。

## 三、被证伪的假设（重点）

这一节是这份复盘存在的主要理由。

### 3.1 加速度计量程：抄了数据手册，错了 61%

初值按数据手册取 `8192 LSB/g`，实测静止时 `|a| = 1.610 g`——错了 61%。

改成 `13189`（8192 × 1.610）后实测 `|a| = 1.004`（1000 样本内 0.989–1.041）。

**局限没有掩盖**：单姿态标定无法把量程误差和零偏误差分开。注释里写明了这一点，
以及"换姿态若仍偏离 1，需要多姿态拟合"。

### 3.2 单元测试全绿，真实并发下 500

`/api/v1/status` 在真实并发下间歇 500：

```
sqlite3.ProgrammingError: SQLite objects created in a thread
can only be used in that same thread
```

根因：FastAPI 把同步依赖和同步端点**分别**丢进线程池，两者不保证落在同一个线程上，
而连接是在依赖里创建的。

**为什么 14 项测试全过却没抓到**：`TestClient` 是串行的，恰好复用了同一个线程。

修法是 `check_same_thread=False`（连接每请求新建、用完即关，依赖先于端点返回，
只是跨线程先后使用，不存在并发访问）。修完用 36 个并发请求验证全部 200。

> **教训**：测试通过 ≠ 正确。测试环境的"恰好"掩盖了真实环境的并发模型。

### 3.3 NTP："新鲜"是自己说的，没有证据

原来的逻辑：把 `g_ntp_synced = false`，调 `configTime()`，再读一次 `time()` 看值合不合理。
合理就标记同步成功。

问题在于 `time()` **必然**合理——系统时钟从上次同步起一直在走。于是每次"重同步"
都把年龄清零，把"没有收到任何应答"报成"刚刚同步过"。**即"新鲜"这个结论本身不可信。**

修法：只在 SNTP 回调里认定为真（`sntp_set_time_sync_notification_cb`），
重同步用 `sntp_restart()` 强制重新查询。实测看到锯齿波：0→240s 增长，收到应答后
归零，0 个批次超过 300 秒。

> 这里先编译验证了 `esp_sntp.h` 和 `sntp_restart()` 确实存在，没有凭印象写——
> 因为之前刚在 I2S 上吃过高估 API 可用性的亏（见 3.5）。

### 3.4 阈值之间的关系没检查，标签退化成常量

`NTP_RESYNC_MS` 原本 30 分钟，而服务端判定"新鲜"的阈值是 300 秒。
30 分钟 ≫ 5 分钟，意味着同步年龄在一路涨到 30 分钟的过程中必然越过 300 秒。

实测 3000/3000 个样本全被标成 `ntp_stale`——**标签变成了常量，等于没有信息**。

改成 4 分钟，留出重试和回调延迟的余量。教训是两个相关的阈值必须放在一起看，
而不是各自取一个"看起来合理"的值。

### 3.5 I2S：想当然地用 PDM API

麦克风按 PDM 处理，写了 `i2s_pdm.h`。实际这块板子是标准 I2S，且 Arduino-ESP32 核心
是 **2.0.17（不是 3.x）**，只有遗留的 `driver/i2s.h`，`i2s_std.h` / `i2s_pdm.h` 根本不存在。

另一个坑：麦克风输出的是"32 位帧内的 24 位数据"，必须按 32 位读再右移 8 位；
按 16 位读会帧错位，得到对声音无反应的小幅乱跳——**看起来像有数据，其实是噪声**。

### 3.6 界面自己打自己的脸

主报警条写"链路正常……时间戳可信"，下面又附了一行"⚠ 窗口内存在非新鲜时间戳"。
两个相反的结论同屏出现。

根因是时间戳可信度被当成"附录"追加，而不是进入报警优先级链。
改成并入主链后，附注行删掉。

### 3.7 纵轴把真实信号压平了

`|a|` 图用 `forceMin: 0.5` 当纵轴地板，浪费了 60% 的面板高度，把 0.99–1.01 的真实
波动压成一条直线——等于没画。改成 `include: [1.0]`：参考值参与量程计算保证在视野内，
但不当地板。

紧接着暴露第二个问题：量程窄时固定 3 位小数会把 5 条刻度印成 `1.000 / 1.000 /
1.000 / 0.999 / 0.999`，纵轴同样等于没有信息。而且**设备静止时跨度就只有千分之几，
这是常态不是异常**。改成按实际刻度间隔自适应精度，位数不够时加宽左侧留白。

### 3.8 "停止采集"被显示成"设备失联"

本轮新增开关时的问题：停止后界面安静下来，和"设备失联"在图上长得一模一样。

这是**直接违背第 3 条要求**的——把用户自己的操作报成故障，比不报还糟。

处理分三层：
1. 报警条区分中性蓝"已停止采集"，图上空白画成灰色而非红色
2. 停止区间从 `control_log` 历史里配对出来，用来把"上传中断"识别成"主动停止"
3. **反向也不能掩盖**：若停止指令下发 14 秒后仍在收到新批次，报
   `a-warn「已下发停止，但仍在收到数据」`，而不是滑进中性提示里去

第 3 条是用独立实例实测的（停 → 等 16 秒 → 灌一批数据），因为这是最危险的失败模式：
一旦被中性提示盖过去，一次真实的失灵就被描述成用户自己的操作。

> 另外还修了一处同类问题：卡片"最近一批距今"在停止状态下仍然标红，
> 和上方蓝色的"已停止采集"同屏矛盾。数字照报，但不着色。

## 四、验证方法：为什么不相信"看起来对"

第 3 条要求（失败必须在界面上被看见）是**否定性**的——正常情况下永远看不到。
所以验证不能靠读代码确认逻辑，必须主动制造失败。

为此建了两个工具，都进了仓库：

**`server/tools/fault_inject.py`** — 对着隔离实例注入 4 种缺陷：seq 缺口、
`dropped_since_last > 0`、NTP 未同步、彻底静默。然后看界面是否分别报警。

**`server/tools/ui_check.mjs`** — 把 `index.html` 里的脚本抠出来，用最小 DOM 桩在
node 里跑，断言报警等级与文案、卡片数值、分段结果。这样"该报警时必须报警"可以被
确定性地回归，不必真去拔电源。

**无头 Edge 截图** — 本环境没有 Playwright/Puppeteer，用
`msedge --headless=new --virtual-time-budget=15000 --screenshot=...` 确认界面真的
渲染正确，而不只是"代码看起来对"。

**独立实例测试** — 端口 8001 + 独立数据库，避免污染真实数据。
本轮测"板子不理会停止指令"和 CORS 预检都用的这个办法。

这套方法确实起了作用：3.2（测试全绿但真实并发 500）、3.3（NTP 假新鲜）、3.6/3.7
（三处界面缺陷）都是这么查出来的，没有一处是靠读代码发现的。

## 五、如果重来

1. **一开始就把"失败可见"当成可测需求**，而不是写完再想怎么验证。
   故障注入器应该和存储层同期出现，而不是等到第 6 阶段。
2. **相关阈值放在一起定义**。3.4 的问题（30 分钟 vs 300 秒）如果两个常量写在同一处，
   写的时候就发现了。
3. **对硬件 API 先编译验证再写逻辑**。3.5 的 PDM 教训。
4. **单姿态标定要在需求里就说清局限**，而不是等事后补注释。

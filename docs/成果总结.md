## 第3周（0.3.0）：按键触发与物理反馈闭环

设计、协议与上板清单见 [`week3-button.md`](week3-button.md)。

### 一、解决了什么

前两周是两条单向链路：设备一直推、网页一直看（第1周），网页下发、设备执行、结果回传（第2周）。
第3周把它们接成**闭环**，并且把"人"放进环里：

```
按下板上按键 → LED 立刻单闪（本地反馈，断网也照样闪）
            → POST /api/v1/button（幂等键 mac+boot_id+press_seq）
            → 网页 2 秒内出现该行「待回应」
            → 操作者点「回应」或「取消」 → 生成一条 op=notify 指令
            → 设备下一次轮询领取 → 播放两下慢闪 / 六下快闪
            → 回执 → 网页同一行变成「成功 · 设备已播放反馈」
```

**没有新造通信链路**：`notify` 就是第2周 `commands` 表里的一条普通指令，
领取协议、状态机、超时结算、事件溯源、在飞上限、幂等键全部复用。
新增的只有"按键事件"这一张表和它自己的三态。

### 二、关键设计

**本地反馈不许依赖网络。** `button_poll()` 放在 `loop()` 里 Wi-Fi 检查**之前**，
`on_press()` 的第一行就是点灯——执行到那一行时事件甚至还没拿到序号。
否则"按了没反应"和"板子死了"在佩戴者眼里是同一件事。

**事件状态只有三态，刻意不加"设备已确认"。** `received / acked / cancelled`
记的是"用户点了什么"；设备到底播放了没有，看 `request_id` 关联的那条指令
（`done/failed/timeout/expired`）。存两份状态迟早漂移，而 `commands` 那一份是权威的、
带完整事件溯源的。代价是列表查询多一次 join，好处是两个面板看到的指令状态永远一致。

**幂等键一层一把，各管一件事。** 板上消抖（30ms）防机械抖动把一次按压记成多个序号——
这种重复**服务端救不了**，因为在板上它们真的是不同序号；
`UNIQUE(device_mac, boot_id, press_seq)` 防 HTTP 重发变成"按了两次"
（新建 201、命中 200+`X-Deduped`，状态码本身就说明这是不是第一次）；
`client_token` 防双击让设备闪两遍灯；`request_id` 防板端重领与回执重放。
`boot_id` 让 `press_seq` 可以每次启动从 0 重来。

**丢事件也要留痕。** 待传队列 8 条、单条重试 10 次（5 秒节流），
队列满或重试用尽都计入 `queue_dropped`，随下一次成功上传带到服务端并在界面上显示
「板上曾丢弃 N 次」。于是"断网期间按了 12 次只上来 9 次"是有证据的，不是"网页少了几行"。

**`respond()` 的顺序决定了能不能自愈。** 先创建指令、成功之后才更新事件行。
反过来的话，一次 429（在飞已满）就会留下一条"已回应但没有指令"的事件，
界面显示成功、设备永远不动、且没有入口重来。

**第一个字符串参数牵出四处改动。** `decision=ack/cancel` 逼出了 `STR` 类型：
OPS 的 kind、`_coerce` 的 enum 白名单、`ops_catalog` 的 `choices`、前端渲染下拉框。
enum 白名单必须在服务端——`decision` 会被拼进用 `;`/`=` 分隔的 claim 文本协议，
允许任意字符串就等于允许伪造参数段。改完之后，前端 `renderOps` 不再假设"参数就是数字"，
**下一个带枚举参数的 op 一行前端代码都不用改**。

### 三、防抖为什么是两层

`button.js` 的回应按钮同时有代码级 `if (busyId !== null) return;` 和 DOM 级 `disabled`。
只有 DOM 级时，在浏览器里看起来完全正确，但 `ui_check.mjs` 的 node 桩直接调 `onclick()`
绕过 `disabled`，三次点击变三次 POST——桩暴露的是真问题：键盘回车连发、辅助功能点击
同样能绕过 `disabled`。现在断言是"连点 3 次 → 1 次 POST 且 `client_token` 唯一"。

### 七、追加：让“插上板子、打开网页就有数据”真正成立

**问题**：插上板子双击 `server/static/index.html`（`file://`）报“无法连接服务端”。

## 第2周（0.2.0）：Web 远程采集指令与执行结果反馈

### 一、解决了什么

第1周只有单向链路：板子一直采、网页一直看。第2周补上反方向的**控制通道**——
网页下发指令，板子真实执行，执行结果（成功/失败/超时/过期/撤销）回传并可追溯。

| op | 作用 | 真机实测 |
|---|---|---|
| `ping` | 验证链路往返，不做采集 | `done`，往返 448 ms |
| `capture` | 指定时长真实采集（上限 10 秒，受 12 秒环形缓冲约束） | `done`，20/20 样本入库且与板端一致 |
| `selftest` | 传感器自检 | `failed` —— 真实偏置超阈值，第1周遗留的标定问题。**如实报失败，不粉饰** |

### 二、关键设计

**状态机**：`pending → claimed → running → {done | failed | expired | timeout | cancelled}`。
`TRANSITIONS` 是唯一一份合法流转表，非法流转直接拒绝并留痕。四个终态各对应一种真实故障：
没人来领（`expired`，设备离线或 MAC 写错）、领了不给结果（`timeout`）、
设备自己报错（`failed`）、用户在设备领取前撤回（`cancelled`）。

**`request_id`**：`req_<9位base36毫秒>_<6位hex随机>`。时间片让人能按先后排查，
随机片让 id 不可猜测——否则任何人都能拼出 id 去伪造回执。同一毫秒内随机片撞车就重抽
（24 位随机空间连续生成时，按生日悖论算碰撞概率不可忽略，测试曾半概率变红）。

**事件溯源**：`commands` 存当前状态，`command_events` 存每一次流转（谁、何时、
从什么到什么、为什么）。状态可以改，历史不能改——"这条指令为什么变成 timeout"
事后必须答得出来。

**三方共用一份实现**：服务端、板端解析、测试都 import `server/commands.py`。
这是真机联调换来的教训：`split_claim` 拒绝空参数段，导致 `ping`/`selftest` 这类
无参指令永远解析失败——服务端认为合法、板子认为非法的分歧，只有共用一份代码才能根除。

**失败不静默**：迟到、错乱、越权的回执一律 4xx 并落事件；在飞指令超
`MAX_LIVE_PER_DEVICE = 8` 返回 429，而不是让队列无限堆积。

### 三、真机联调修掉的 3 个固件 bug

只有插上真板子才暴露，仿真和单测都盖不住：

1. `split_claim` 拒绝空参数段 → 无参指令永远解析失败（见上）。
2. 手拼 JSON 开头多一个逗号（`{,"k":...`）→ 所有终态回执被服务端 422 打回，
   指令永远停在 `running`。
3. 终态回执失败后设备**重跑整条采集** → 卡住十几分钟堵死队列。改为记住 `g_done_rid`
   与待补发内容，只补发回执、不重跑采集。

### 四、"板子插上了网页却没数据"的根因与固化

排查了一个多小时，根因不在代码：Windows 防火墙里有一条**拦住全部入站**的 Block 规则
（沙箱环境加的）。**Block 优先级高于 Allow**，所以"已经放行 8000"完全无效——
板子只报 `[uplink] HTTP -1`，而服务端日志里一条请求都看不到。

把这套排查顺序固化成工具，下次几分钟定位：

| 文件 | 作用 |
|---|---|
| `server/tools/doctor.py` | 按数据流向 11 项体检，FAIL 直接给可粘贴的修复命令。只读，不改系统 |
| `server/tools/fix_firewall.ps1` | 禁用全局入站拦截（只禁用不删除，可还原）+ 放行端口，自动提权 |
| `docs/board-connect-checklist.md` | 人读的清单：一分钟版流程、完整七步、症状速查表、换热点后必做三件事 |

最容易忘的一条：`secrets.h` 里的 `SERVER_URL` 是**写死在固件里**的，
手机热点重连后本机 IP 会变，此时必须改 IP 并**重新烧录**，光重启服务端没用。

## 第1周（0.1.0）：传感数据采集与 Web 展示（2026-09-19）

### 一、这轮解决的两个问题

#### 1. 双击打开 `index.html` 看不到数据

**原因**：`file://` 协议下相对路径会被解析成 `file:///api/v1/...`，永远取不到数据。

**修法**：页面改为自动判断来源——由服务端提供时走同源相对路径，从文件系统打开时
换用绝对地址（`?api=` 参数 > localStorage > `127.0.0.1:8000`），服务端同时开启 CORS
（`file://` 的 Origin 是字符串 `null`，不开中间件浏览器会拦掉所有响应）。

**要说清楚的一点**：这只是让页面能找到服务端。**服务端必须一直在运行**——数据存在
它的 SQLite 里，光有一个 HTML 文件变不出数据。因此补了 `start_server.bat`，
可以自己双击启动，不依赖我的会话。

#### 2. 开始/停止采集按钮

实现为**控制板子真的停采**，不是网页暂停刷新。

---

### 二、设计上的关键取舍

#### 停止采集绝不能被显示成"设备失联"

停止后界面安静下来，和"设备失联"在图上长得一模一样。这是本轮最需要小心的地方，
因为它直接关系到"失败必须被看见"这条要求——把用户自己的操作报成故障，比不报更糟。

| 情况 | 界面表现 |
|---|---|
| 用户主动停止 | 中性蓝「已停止采集」，图上空白画成**灰色**带并标注 |
| 设备重启 | **红色**带（真故障） |
| 下发停止但板子还在传 | 黄色 `a-warn「已下发停止，但仍在收到数据」` |

第三行是最危险的失败模式：一旦被中性提示盖过去，一次真实的失灵就被描述成用户自己的
操作。是用**独立实例**实测的（停止 → 等 16 秒 → 灌一批数据），界面正确报出警告。

`control_log` 表只记"变更"，当前状态取最后一条，不另设单行表——同一个事实存两处
必然会漂移，和 `trust_level` 不落库是同一个道理。保留历史则是因为：一段空白到底是
用户按了停止还是设备坏了，光看图分不出来，只能靠这个区间去对。

#### 板端默认采集

轮询不到服务端时维持现状，不因为一次网络抖动就自行停采。停止只停"采样"、不停
"上传"，缓冲区里已经采到的样本照常传完——按一次停止就丢掉手上已有数据，
等于让用户的操作毁掉数据。

### 五、需要你决定的事

1. **按钮的理解对不对。** 我实现的是"控制板子真的停采"。如果你其实只想让网页暂停
   刷新，说一声——服务端和固件的改动可以回退，只保留页面部分。

2. **部署时必须设置 `CONTROL_TOKEN` 和 `INGEST_TOKEN`**（`server/.env`）。
   现在控制接口在局域网里是敞开的，公网不设的话任何人都能远程把采集停掉，
   而你在界面上只会看到"设备失联"。

3. **VPS 部署（唯一未完成的任务）仍缺信息**：服务器 IP、系统、登录方式，
   以及有没有域名（决定能不能上 HTTPS）。当前 `X-Ingest-Token` 是明文传输的，
   鉴权要真正有意义必须配合 HTTPS。

### 六、仍未解决的问题

- **采样率约 16.6 Hz**，低于配置的 20 Hz。每轮循环有一次阻塞式 I2S 读取（约 16ms）。
  `t_device_ms` 如实记录，数据本身不误导，但抖动未处理。
- **断电时未上传的缓冲样本不计入任何计数器**，只能表现为 `boot_id` 变化
  加上服务端接收时刻的空白。
- **加速度计只做了单姿态标定**，无法把量程误差和零偏误差分开。
- **`/api/v1/readings` 的 `since_ms` 过滤的是设备启动内毫秒数**，跨重启无意义。
  界面刻意不用它，但接口仍然敞着，是个陷阱。
